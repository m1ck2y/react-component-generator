# TDD 규칙

> ⚠️ **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.**
> 적용 대상이면 예외 없이 아래 사이클을 따른다. 단계를 건너뛰거나 순서를 바꾸지 않는다.

## 우선순위

- 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 프로젝트 규칙이 없을 때 쓰는 **기본값(fallback)**이다.
- 프로젝트 규칙이 일부만 다루면, 다루지 않은 부분은 이 파일을 따른다.

## 적용 기준

| 반드시 적용 | 적용 불필요 |
|---|---|
| 비즈니스 로직 | 타입 정의 (`type`, `interface`) |
| API 핸들러·엔드포인트 | 설정 파일 (`*.config.*`, `tsconfig`, `.env.example` 등) |
| 유틸리티·순수 함수 | 순수 UI (로직 없는 마크업·스타일) |
| **버그 수정** (재현 테스트 먼저) | SQL (스키마·마이그레이션·쿼리 파일) |

- 판단이 애매하면 **적용 대상으로 본다.**
- UI라도 조건 분기·상태 전이·이벤트 처리 로직이 있으면 그 로직은 적용 대상이다.

## RED-GREEN-REFACTOR

### 1. RED — 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 검증하지 않는다.
- 테스트 이름에 기대 동작을 적는다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 테스트는 RED가 아니다.
- **실패 이유가 "기능 미구현"이어야 한다.** 오타·import 오류·문법 오류·잘못된 테스트 설정으로 실패했다면 RED가 아니다. 테스트를 고쳐 다시 실행한다.
- 처음부터 통과하는 테스트는 아무것도 검증하지 못한다. 테스트를 다시 작성한다.

### 2. GREEN — 통과시키는 최소 코드

- 방금 실패한 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI**: 테스트가 요구하지 않는 분기·옵션·추상화·일반화를 넣지 않는다.
- **신규 테스트 + 기존 테스트 전체가 통과**하는 것을 실행해서 확인한다. 기존 테스트가 깨지면 GREEN이 아니다.

### 3. REFACTOR — 동작 유지한 채 정리

- 할 일: **중복 제거, 이름 개선, 헬퍼 추출.**
- 변경할 때마다 테스트를 실행해 **green을 유지**한다.
- **새 동작 추가 금지.** 새 동작이 필요하면 RED로 돌아간다.
- 정리할 것이 없으면 건너뛰어도 된다.

### 4. 반복

- 다음 동작을 하나 골라 **RED로 돌아간다.**
- 구현할 동작이 남지 않을 때까지 반복한다.

## 삭제 강제 규칙

- **테스트보다 프로덕션 코드를 먼저 작성했다면 그 코드를 삭제하고 RED부터 다시 시작한다.**
- **"참고용"으로 남기는 것도 금지한다.** 주석 처리, 다른 파일로 옮기기, 임시 브랜치 보관 모두 해당한다.
- 이미 존재하던 테스트 없는 코드를 수정할 때는, 수정하려는 동작에 대한 테스트를 먼저 작성하고 RED를 확인한 뒤 수정한다.

## 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트 불필요" | **단순하면 테스트도 1분이면 끝난다.** 단순한 코드일수록 나중에 조건이 붙으며 깨진다. |
| "나중에 추가하겠다" | **나중은 오지 않는다.** 구현 후에 쓴 테스트는 코드에 맞춰 쓰여 실패를 본 적이 없으므로 검증력이 없다. |
| "시간이 없다" | **디버깅이 더 오래 걸린다.** 테스트 없이 아낀 시간은 회귀 버그로 되돌아온다. |
| "삭제하면 낭비" | **매몰 비용이다.** 테스트 없이 쓴 코드는 검증되지 않은 초안이고, 다시 쓰면 더 작고 정확해진다. |
| "프로토타입이다" | **프로토타입은 그대로 프로덕션이 된다.** 버릴 코드라면 적용 대상 밖에서 작성하고, 남길 코드라면 TDD로 다시 쓴다. |
