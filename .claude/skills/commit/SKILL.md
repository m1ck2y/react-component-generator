# commit

변경사항을 읽고, 리뷰어가 히스토리만 보고도 무엇이 왜 바뀌었는지 알 수 있게 커밋을 만든다. 커밋은 되돌리기 번거로운 작업이므로 **계획을 먼저 보여주고 승인받은 뒤에만 실행**한다.

## 1. 변경사항 수집

아래 명령으로 전체 그림을 먼저 잡는다.

```bash
git status --porcelain
git diff                 # 스테이징 안 된 변경
git diff --cached        # 이미 스테이징된 변경
git log --oneline -10    # 기존 메시지 스타일 참고 (커밋이 없으면 생략)
```

놓치기 쉬운 경우:
- **새 파일(`??`)은 `git diff`에 나오지 않는다.** 파일을 직접 읽어 내용을 파악한다. 첫 커밋 저장소라면 전부 새 파일이다.
- **lock 파일·빌드 산출물·바이너리**(`bun.lock`, `package-lock.json`, 이미지, PDF 등)는 내용을 다 읽지 말고 "의존성 잠금 갱신"처럼 성격만 파악한다.
- 사용자가 이미 일부를 스테이징해 두었다면, 그 범위를 의도된 묶음으로 존중하고 계획에서 따로 표시한다.

## 2. 커밋 대상에서 제외할 것

다음은 커밋 계획에 넣지 말고 사용자에게 위치만 알린다. 값은 출력하지 않는다.
- `.env`, `*.pem`, `id_rsa`, 자격증명 파일 등 비밀정보가 담긴 파일
- diff 안에 API 키·토큰·비밀번호·접속 문자열로 보이는 값 (예: `파일명:행번호에 API 키로 보이는 값이 있습니다`)
- `.gitignore`에 넣어야 할 것 같은 산출물(`dist/`, `node_modules/`, 로그 등)이 추적 대상으로 잡힌 경우 → `.gitignore` 수정을 제안

한 번 커밋되면 히스토리에 남아 지우기 어렵기 때문에, 애매하면 빼고 물어본다.

## 3. 논리적 단위로 분류

"이 커밋 하나만 되돌려도 말이 되는가?"를 기준으로 묶는다.

- 한 기능의 구현 + 그 테스트 + 관련 타입 변경 → 한 커밋
- 버그 수정과 무관한 리팩터링이 섞여 있으면 → 분리
- 포맷팅·설정·의존성 변경 → 기능 커밋과 분리
- 한 파일 안에 성격이 다른 변경이 섞여 있어도 기본은 파일 단위로 묶는다. 부분 스테이징(`git add -p`)은 대화형이라 쓸 수 없으므로, 꼭 나눠야 하면 사용자에게 알리고 판단을 맡긴다.
- 변경이 작고 하나의 의도라면 억지로 쪼개지 않는다. 커밋 1개가 정답인 경우가 많다.

커밋 순서는 의존 관계를 따른다(예: 공용 함수 추가 → 그 함수를 쓰는 기능).

## 4. 커밋 메시지 작성

형식:

```
<type>: <한국어 요약>

<본문 (선택)>
```

**type** (이 네 가지만 사용):
| type | 언제 |
|---|---|
| `feat` | 사용자가 체감하는 새 기능·동작 추가 |
| `fix` | 버그 수정, 잘못된 동작 교정 |
| `refactor` | 동작 변화 없는 구조 개선 |
| `chore` | 설정, 빌드, 의존성, 문서, 테스트 추가, 기타 잡무 |

경계가 애매하면 사용자 관점에서 판단한다. 예: 보안 취약점 수정은 `fix`, 테스트만 추가했으면 `chore`.

**요약 줄**:
- 50자 안팎, 끝에 마침표 없음
- 명사형으로 끝낸다: "추가", "수정", "제거", "분리", "개선"
- 무엇을 했는지가 드러나게 쓴다. "코드 수정", "업데이트" 같은 막연한 표현은 피한다.

**본문**: 요약만으로 이유가 드러나지 않을 때만 쓴다. "왜" 바꿨는지, 주의할 점이 무엇인지를 `- ` 목록으로 짧게 적는다.

예시:
```
fix: Gemini API 키를 URL 쿼리 대신 헤더로 전송

- 쿼리스트링의 키가 프록시·로그에 남는 문제 방지
```
```
feat: 생성 결과를 localStorage에 저장해 새로고침 후 복원
```
```
chore: 프로젝트 초기 구성 추가
```

## 5. 승인 요청

실행 전에 아래 형식으로 계획을 보여주고 **응답을 기다린다**. 승인 없이 커밋하지 않는다.

```
커밋 계획 (2건)

[1] fix: Gemini API 키를 URL 쿼리 대신 헤더로 전송
    - server/index.ts

[2] chore: generator 단위 테스트 보강
    - server/generator.test.ts

제외: .env (비밀정보 포함 가능)

이대로 진행할까요? (수정할 메시지나 묶음이 있으면 알려주세요)
```

사용자가 메시지나 묶음을 고치라고 하면 반영한 계획을 다시 보여주고 승인을 받는다. "그냥 해", "진행"처럼 명확히 승인하면 실행한다.

## 6. 커밋 실행

커밋마다:

```bash
git add -- <파일1> <파일2>      # 계획에 있는 파일만 명시적으로
git commit -m "<요약>" -m "<본문>"   # 본문 없으면 -m 하나
```

- `git add -A`나 `git add .`는 쓰지 않는다. 계획에 없는 파일(특히 2단계에서 뺀 파일)이 딸려 들어가기 때문이다.
- 사용자가 미리 스테이징한 내용이 있는데 다른 묶음부터 커밋해야 한다면, 섞이지 않게 순서를 조정하거나 사용자에게 확인한다.
- `--no-verify`, `--amend`, `push`는 사용자가 명시적으로 요청하지 않으면 하지 않는다.
- pre-commit 훅이 실패하면 원인을 보고하고, 고친 뒤 **새 커밋**으로 다시 시도한다(amend 아님). 훅이 파일을 자동 수정했다면 그 파일을 다시 add한다.

## 7. 결과 보고

모든 커밋이 끝나면 `git log --oneline -<커밋 수>`와 `git status --short`로 확인하고 짧게 보고한다.
- 만든 커밋 목록 (해시 + 요약)
- 커밋하지 않고 남은 변경이 있으면 그 목록과 이유
